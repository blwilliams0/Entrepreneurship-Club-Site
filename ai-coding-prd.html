How to get AI to code entire pieces of software for you

AI coding agents can help you build software projects at 40,000+ lines. The real skill is telling the AI exactly what to build.

Line count is not a quality metric. “40,000+ lines” shows the scale AI coding agents can help with. It does not mean more code is better.

The leverage is not typing code faster. It is turning an idea into a clear specification, letting AI build from that specification, testing what it made, and iterating.

From idea to working software

A coding agent is powerful, but it cannot read your mind. This process reduces the number of product decisions the AI has to invent for you.

Product design comes after evidence

If you are building a business, do not use a beautiful PRD as a substitute for learning whether real people actually care. Talk to potential users, test the problem, and collect evidence. Then use the PRD to define the product you are going to build.

Tip: open the Google Doc and choose File, then Make a copy, to get your own version you can write notes in.

What is a PRD?

PRD stands for Product Requirements Document. It explains what the product should do, who it is for, why it should exist, what belongs in the first version, and what observable behavior counts as “done.”

Think of the PRD as a communication layer

Your idea lives in your head. The PRD converts that idea into something another person, or an AI coding agent, can understand and execute with less guessing.

A useful PRD is

  • User-centered: it starts with the person, problem, and desired outcome.
  • Specific: important product behavior is written down instead of implied.
  • Scoped: it is clear what belongs in this version and what does not.
  • Testable: important requirements have observable acceptance criteria.
  • Editable: it is a living document that changes when you learn something important.

A PRD is not

  • The code itself.
  • A substitute for talking to users.
  • A technical architecture document.
  • A promise that every feature idea belongs in version one.
  • Something the AI should invent for you without asking questions.
Part 1

Get clear on the product before features

Start with these questions

  1. What are you making? Name the product or service in plain language.
  2. Who is it for? “Everyone” is almost never useful. Name the primary user or customer.
  3. What problem, desire, job, or opportunity exists? Describe the user’s situation before talking about features.
  4. What change are you trying to create? What should become easier, faster, safer, cheaper, more fun, or more possible?
  5. When would they use it? Describe a real situation, not a generic feature list.
  6. What evidence do you have? For a business-focused project: what have real users said or done that suggests this matters?

Weak vs. stronger product intent

Weak

“Make an app that helps students network.”

Stronger

“CSUMB student builders often meet interesting people once and then lose the connection. Build a lightweight directory where members can share what they are building, what they can contribute, and who they want to meet, so the club can create thoughtful introductions.”

Ask: what did the stronger version tell the builder that the weak version did not?

Part 2

Make it buildable

MVP

Ask: “What is the smallest coherent version that delivers the core value?”

  • MVP does not mean broken, sloppy, or five half-built ideas.
  • It means high craftsmanship on a disciplined footprint.
  • Decide what must exist first, and cut distractions.

Core feature tiers

TierMeaning
P0: Must haveThe product fails to solve the core problem without it. Required on day one.
P1: Nice to haveValuable, but the first version can still succeed without it.
P2+: LaterFuture expansion or “cool” ideas that distract from validating the core value.

User flows

Ask: “What does the person actually do, step by step?” Think this through for your customer.

Example

User arrives, understands the value proposition, signs up, chooses preferences, and receives the first useful result.

Acceptance criteria

For each must-have requirement, define the observable behavior that proves it works.

Instead of

“Build a meeting page.”

Write

“A visitor can see the next meeting date, time, location, and a clear action to join without navigating to another page.”

Non-goals

Tell the AI what not to build. Explicit non-goals are one of the easiest ways to prevent feature creep.

If the AI has to guess, it will guess

Every unresolved ambiguity should become one of three things:

1. A decision

A product tradeoff you still need to resolve yourself.

2. A PRD detail

A requirement, rule, boundary, or behavior you write explicitly.

3. An AI flag

An instruction telling the coding agent to stop and ask you instead of inventing an answer.

The goal is not the longest PRD

The goal is to reduce guessing. A short, precise PRD can be better than a long document full of vague prose.

Prompt: build the PRD with you

Start with an interview, not an instant rewrite. Paste these into the AI tool of your choice.

Interview prompt

Act as an experienced product manager and interviewer. I am going to describe a product or business idea.

Your job is to help me create a strong Product Requirements Document without inventing important product decisions for me.

Ask me one question at a time. Start with the user, problem, evidence, product vision, and primary use cases. Then move into MVP scope, core features, user flows, requirements, acceptance criteria, non-goals, assumptions, constraints, risks, design references, and open questions.

When my answer is vague, ask a follow-up question instead of filling in the gap yourself.

Do not start coding. Do not choose a technical stack unless I ask you to.

Once the important questions are answered, produce a clean PRD in Markdown that preserves my intent and clearly marks any unresolved questions.

If you already have a rough idea

Ask me questions one at a time until you understand the user, problem, and product vision. Do not design features yet. Challenge my assumptions and tell me what evidence I am missing.

Use AI to find what is still unclear

Refine before you code. Give the AI your draft PRD along with one of these prompts.

Full PRD audit

I'm going to give you a draft PRD. Act as an experienced product manager helping me make it specific enough that an AI coding agent could build from it with as little guessing as possible.

First, do not rewrite it yet.

Review the PRD and clearly point out:
- what is vague or ambiguous
- what an AI developer would still have to guess
- where the MVP is unclear
- which features appear to be core versus optional
- which user flows need to be explained more clearly
- assumptions I may be making
- contradictions or missing information
- anything that could cause the finished product to differ from what I actually intend

Explain why each issue matters.

Then ask me the most important unanswered questions one at a time.

Once I answer enough questions, rewrite the PRD to make it clearer and more buildable while preserving my original intent.

Do not invent important product decisions. If something matters and you do not know the answer, ask me.

MVP, core features, and user flows

Help me make this PRD more specific and buildable.

Focus especially on:
1. My MVP: what is the smallest useful version that delivers the core value?
2. My core features: what absolutely needs to exist in the first version?
3. My user flows: what does the user actually do, step by step?

Identify anything vague, missing, or something an AI coding agent would have to guess.

Ask me questions one at a time instead of making important decisions for me.

Help me separate must-have features, nice-to-have features, and things that should wait until later.

Hard-mode developer critique

Pretend you are the AI developer who has to build this product tomorrow using only this PRD.

What would you still have to guess?

Identify every important ambiguity, missing decision, unclear user flow, vague requirement, unnecessary feature, or assumption that could cause you to build the wrong product.

Do not fix those things by making up answers. Ask me the questions you would need answered.

Do not start by saying “build it”

Put the PRD inside the project so it becomes persistent context. A simple starting structure:

/PRD.md
/README.md
/src/ ...
/public/ ...

Then open your coding agent in the repository and make it prove that it understands the product before it writes code.

Implementation-plan prompt

Read PRD.md carefully.

Do not start coding yet.

First:

1. Summarize the product you believe I am asking you to build.

2. Identify any remaining ambiguity or unanswered questions.

3. Propose an implementation plan in logical phases.

4. Identify the smallest end-to-end version we should build first.

5. Explain the main pages/components and user flows you expect to implement.

6. Identify any external services, APIs, databases, authentication, or other dependencies you think are required.

Do not make major product decisions that are not supported by the PRD. Ask me instead.

Wait for my approval before beginning implementation.

After you approve the plan

Go ahead and implement the first working version according to the approved implementation plan and PRD.

Prioritize the core user flow and MVP. Test important functionality as you go.

If you reach an important product decision that the PRD does not answer, stop and ask me rather than guessing.

Keep the implementation aligned with the PRD. If you believe the PRD should change, explain why before changing the product direction.

Treat the PRD as a living source of truth

Build, test, revise:

  1. Build one coherent slice of the product.
  2. Test it against the acceptance criteria and important user flows.
  3. Inspect the actual experience, not just whether the code runs.
  4. Write down what changed or what you learned.
  5. Update the PRD when the product decision changes.
  6. Commit meaningful milestones to GitHub.
  7. Repeat until the product is ready to launch.
Do not optimize for raw code volume

The goal is working software that solves the intended problem. Delete unnecessary code, simplify aggressively, and keep the implementation understandable.

Final principle

You do not need to know how to manually write every line of the software. You do need to think clearly about the customer, the product, the tradeoffs, and what “done” means. Better specification gives the AI less room to build the wrong thing.
